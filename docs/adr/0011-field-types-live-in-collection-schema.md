# Field Types live in the Collection Schema, and Indexes take theirs from it

Each field's Field Type is declared once in the Collection's Collection Schema, stored in its Catalog entry, and an Index on the field covers values of that type rather than declaring one of its own. The Collection Schema knows nothing about Indexes. Per-Index types would let two Indexes on one field disagree about what that field may hold, so whether a write is accepted would depend on which Indexes happen to exist. The schema arrives in v0.3 holding only field types, years before v0.8 validation; v0.8 extends this same schema rather than adding a second one.

## Consequences

- Collections stay schemaless by default: a Document whose field holds another type is left out of the Index. Stored Documents are never changed; coercion happens only when building Index keys.
- Rejecting wrongly typed writes is the schema's job, never an Index's: a field declared strict rejects them with Type Mismatch whether or not it is indexed, and a unique Index can only be created on a strict field. An Index that rejected writes itself would bring back the problem this ADR exists to avoid.
- Numbers have two Field Types, `int` and `double`. An Index on an `int` field still includes Documents holding a double there, keyed under the double's floor; an Index on a `double` field keys an integer as the nearest double. Only the Index key is converted: the Document keeps `30.5`, and the Index files it under `30`. Because different values can share a key, queries read inclusive bounds and recheck the filter against the Document itself. Leaving the other kind of number out of the Index instead would miss matches, because filters compare ints and doubles as numbers.
- A strict field rejects any value that does not convert exactly to its type: a strict `int` accepts `30.0` (which JavaScript clients send for `30`) but rejects `30.5`; a strict `double` rejects integers beyond 2⁵³ and NaN (±Infinity are fine). Missing and null are allowed and never collide in a unique Index.
- NaN is left out of every Index: it matches no filter comparison an Index could answer, not even equality with itself.
- An Index can only be created on a field whose type the Collection Schema already declares, and that type cannot be changed or removed while an Index on the field exists: drop the Index, change the type, re-create it. Re-typing never triggers a hidden rebuild. Likewise, making a field strict scans the Collection and fails with Type Mismatch if any Document breaks the rule, and a strict field cannot be relaxed while a unique Index on it exists.
- Index entries point to Document IDs, never to physical locations, and a write whose indexed value is unchanged writes nothing to that Index: the existing entry stays valid because every lookup fetches the Document at its Snapshot and rechecks. This avoids PostgreSQL's write amplification, where an update adds an entry to every index because entries point to row addresses (Uber's main reason for moving to MySQL in 2016), at the cost of a second lookup per Index hit, as in InnoDB.
- Changing the Collection Schema rewrites the Collection's Catalog entry, so concurrent writers abort with Collection Changed.
