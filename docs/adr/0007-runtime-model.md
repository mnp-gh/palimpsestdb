# tokio front end with dedicated threads for the log and CPU work

Client connections run as async tasks on `tokio`; WAL appends and fsyncs go to a dedicated group-commit thread; CPU-heavy work (large sorts, aggregations) goes to a thread pool (`rayon` or `spawn_blocking`). We rejected thread-per-core runtimes (glommio, monoio on io_uring) despite their performance because they are Linux-only and the primary development machine is macOS, and rejected thread-per-connection because it scales poorly with idle clients. Versions before v0.4 are single-threaded. From v0.4 the Database Layer is thread-safe for embedded use with plain threads: one Node is shared by every thread, and a Transaction is used by one thread at a time but may move between threads. The async model arrives in v0.6, once the transaction core is stable.
